# Най-добри практики за HTTP gateways

По-долу са изброени различни най-добри практики за използване на IPFS gateways. За да научите повече за концепциите зад IPFS gateways, включително как работят, наличните доставчици и типовете, вижте [IPFS Gateway](../concepts/ipfs-gateway.md). За информация за отстраняване на проблеми вижте [Отстраняване на проблеми](./troubleshooting.md).

## Избиране на тип gateway за използване

Предпочитаният начин за достъп през gateway варира в зависимост от характера на целевото съдържание. Научете повече за всеки тип gateway и как работи [тук](../concepts/ipfs-gateway.md#gateway-types).

| Цел                                            | Предпочитан тип gateway | Канонична форма на достъп <br> функции и съображения                                                                                                                                                                                                                                                                                                                                                          |
| ---------------------------------------------- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Текуща версия на <br>възможно променящ се root | IPNS subdomain          | `https://{IPNS identifier}.ipns.{gatewayURL}/{optional path to resource}` <br> + поддържа сигурност между източници <br> + поддържа споделяне на ресурси между източници <br> + подходящ за hash IPNS имена; имена на домейн IPNS трябва да бъдат [вградени в един DNS label](https://specs.ipfs.tech/http-gateways/subdomain-gateway/#host-request-header), например `docs.ipfs.tech` става `docs-ipfs-tech` |
|                                                | IPFS DNSLink            | `https://{example.com}/{optional path to resource}` <br> + поддържа сигурност между източници <br> + поддържа споделяне на ресурси между източници <br> – изисква актуализация на DNS, за да се разпространи промяната към root съдържанието <br> • DNSLink, а не потребител/приложение, определя gateway, който да се използва, отваряйки възможни проблеми с доверие и претоварване на gateway              |
| Непроменящ се root или <br> съдържание         | IPFS subdomain          | `https://{CID}.ipfs.{gatewayURL}/{optional path to resource}` <br> + поддържа сигурност между източници <br> + поддържа споделяне на ресурси между източници                                                                                                                                                                                                                                                  |

Всеки тип gateway предоставя мост за приложения без нативна поддръжка на IPFS. По-добра производителност и сигурност се постига чрез нативна IPFS реализация в самото приложение.

## Самостоятелно хостване на gateway

Ако стартирате IPFS възел, който също е конфигуриран като IPFS gateway, всяка от следните съвети може да помогне за подобряване на откриването и възможността за извличане на вашите CIDs.

Ако се преместите извън публичните gateways `ipfs.io` или `dweb.link`, вижте [Replace public gateways with self-hosted IPFS](./replace-public-gateways-with-self-hosted-ipfs.md) за миграционен път с минимални промени.

- Закрепете (pin) вашите CIDs на множество IPFS възли, за да осигурите надеждност и устойчивост при повреди на възли и мрежови разделения. За да улесните pinning, използвайте vendor-agnostic [Pinning Service OpenAPI Specification](https://ipfs.github.io/pinning-services-api-spec/), която вече е [поддържана от много IPFS възлови реализации, клиентски библиотеки и съществуващи pinning услуги](https://github.com/ipfs/pinning-services-api-spec#adoption).
- Използвайте собствен домейн, който притежавате, като ваш IPFS gateway за гъвкавост при внедряване на оптимизации на производителността. Можете да направите това по един от следните начини:
  - Насочете домейн, който притежавате, например `mydomain.ipfs.yourdomain.io`, към reverse proxy като nginx, който ще проксира заявки към публичен gateway, позволявайки ви да сменяте публичните gateways при прекъсване на работа.
  - Използвайте услуга като [Cloudflare workers](https://workers.cloudflare.com/) или [Fastly Compute@Edge](https://www.fastly.com/products/edge-compute), за да внедрите лек reverse proxy към gateway.
- Настройте [peering](./peering-with-content-providers.md) с pinning услугите, които pin-ват вашите CIDs.
- Уверете се, че вашият възел е публично достъпен.
  - Можете да проверите достъпността на вашия възел, като стартирате `ipfs id` и проверите за стойността `/ipfs/kad/1.0.0` в списъка с протоколи (или в една команда, като стартирате `ipfs id | grep ipfs\/kad`).
  - Ако вашият възел не е достъпен, защото сте зад NAT, вижте документацията за [NAT configuration](./nat-configuration.md).
- Уверете се, че коректно връщате HTTP cache headers към клиента, ако IPFS gateway възелът е зад reverse proxy. Обърнете специално внимание на заглавията `Etag`, `Cache-Control` и `Last-Modified`. Обмислете използването на списъка с CIDs в `X-Ipfs-Roots` за по-интелигентни HTTP caching стратегии.
- Поставете CDN като Cloudflare пред IPFS gateway.
- Обмислете активирането на [Accelerated DHT Client](https://github.com/ipfs/kubo/blob/master/docs/config.md#routingaccelerateddhtclient).
- Тестване и наблюдение на скоростта на интернет връзката с инструмент като [Speedtest CLI](https://www.speedtest.net/apps/cli).
- Наблюдавайте дисковия I/O и се уверете, че няма други процеси, причиняващи I/O bottleneck с инструмент като [iotop](https://github.com/Tomas-M/iotop) или [iostat](https://github.com/sysstat/sysstat).

## Избягване на централизация

Използването на gateway изисква адресиране по местоположение: `https://{gatewayURL}/ipfs/{CID}/{etc}`. Много лесно URL адресът на gateway може да стане идентификаторът, по който потребителите идентифицират съдържанието; т.е. uniform resource locator (URL) е неправилно възприеман като uniform resource identifier (URI). Сега си представете, че gateway е офлайн или не е достъпен от другото местоположение на потребителя поради защитни стени. В този момент съдържанието, неправилно идентифицирано от този gateway URL, също изглежда недостъпно, което отменя ключово предимство на IPFS: децентрализацията.

По същия начин, уебсайт, обслужван чрез DNSLink, изпраща всички заявки през един единствен gateway, избран от собственика на домейна: записите `A`/`AAAA`/`CNAME` на домейна сочат към този gateway, докато низът `dnslink={value}` в DNS TXT записа само именува съдържанието за обслужване. Ако избраният gateway стане претоварен, офлайн или компрометиран, уебсайтът става недостъпен или съмнителен.

## Използване на subdomain gateway за изолация на произхода

За да предотвратите една уебстраница да има неправомерен достъп до HTTP сесийни данни, свързани с различна уебстраница, [политиката за един и същи произход](https://en.wikipedia.org/wiki/Same-origin_policy) позволява достъп до скриптове само на страници, които споделят общо име на домейн и порт.

Помислете за два CIDs, всеки от които представлява различен уебсайт, достъпен в стил на path resolution:

- `https://ipfs.io/ipfs/{CID A}/{website A}`
- `https://ipfs.io/ipfs/{CID B}/{website B}`

От гледната точка на браузъра и двете страници споделят общ произход: gateway, идентифициран в URL `https://{gatewayURL}/...`, така че политиката за един и същи произход не защитава една уебстраница от друга.

За да гарантирате сигурността, осигурена от политиката за един и същи произход, използвайте subdomain gateway. Препратката на gateway към двете страници става:

```bash
https://{CID A}.ipfs.{gatewayURL}/{website A}
https://{CID B}.ipfs.{gatewayURL}/{website B}
```

Тези страници не споделят един и същи произход. По подобен начин използването на DNSLink gateway избягва нарушаването на политиката за един и същи произход. [IPFS public gateway checker](https://ipfs.github.io/public-gateway-checker/) идентифицира тези публични gateways, които избягват нарушаването на политиката за един и същи произход.

## Споделяне на ресурси между източници (CORS)

[CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/CORS) позволява на уебстраница да разреши достъп до определени данни от страници с различен произход. [IPFS public gateway checker](https://ipfs.github.io/public-gateway-checker/) идентифицира тези публични gateways, които поддържат CORS.

## Уязвимост тип "man-in-the-middle" в gateway

Използването на публичен или частен HTTP gateway жертва край-to-край криптографската верификация на доставката на правилното съдържание. Помислете за случая, в който браузър извлича съдържание с URL `https://ExampleGateway.com/ipfs/{cid}`. Компрометиран `ExampleGateway.com` създава уязвимости от тип man-in-the-middle, включително:

- Замяна на фалшиво съдържание вместо действителното съдържание, извлечено чрез CID.
- Пренасочване на копие от заявката и отговора, както и на IP адреса на запитващия браузър, към трета страна.

За да се справите с това излагане, клиентите трябва да предпочитат [доверени и проверими типове отговори](../reference/http/gateway.md#trustless-verifiable-retrieval) и да проверят, че върнатите байтове съответстват на заявения CID.

## Предполагаеми имена на файлове при изтегляне

При изтегляне на файлове браузърите обикновено предполагат името на файла, като гледат последната част от пътя, например `https://{domainName/tld}/{path}/userManual.pdf` изтегля файл, съхранен локално под името `userManual.pdf`. За съжаление, когато се свързва директно към файл без съдържаща директория в IPFS, CID става последната част. Съхраняването на изтегления файл с името, зададено на CID, не отговаря на критерия за дружелюбен дизайн.

За да заобиколите този проблем, можете да добавите параметър `?filename={filename.ext}` към query string, за да зададете предварително име за локално съхранения изтеглен файл:

| Стил      | Query                                                                                                                                                      |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Path      | `https://{gatewayURL}/ipfs/{CID}/{optional path to resource}?filename={filename.ext}`                                                                      |
| Subdomain | `https://{CID}.ipfs.{gatewayURL}/{optional path to resource}?filename={filename.ext}`                                                                      |
| DNSLink   | `https://{example.com}/{optional path to resource}` или <br> `https://{gatewayURL}/ipns/{example.com}/{optional path to resource}?filename={filename.ext}` |

## Остарели кешове

Gateway може да кешира DNSLinks от DNS TXT записи, които по подразбиране имат срок на валидност от един час. След промяна на съдържанието кешираните DNSLinks продължават да сочат към вече остарелия CID. За да ограничите доставката на остаряло кеширано съдържание, операторът на домейна трябва да промени параметъра TTL (time-to-live) на DNS записа на минута `60`.
