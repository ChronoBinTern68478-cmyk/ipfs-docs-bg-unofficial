# Възли

Участниците в мрежата IPFS се наричат възли. Възел е инстанция на IPFS реализация, която стартирате на локалния си компютър (директно или през браузър), за да съхранявате файлове и да се свързвате с мрежата IPFS. Те са най-важният аспект на IPFS. Без IPFS възли нямаше да има IPFS мрежа.

Вероятно ще срещнете термина node (възел) в цялата документация на IPFS, в проблеми и в свързания код. Това е много общ термин, така че значението му зависи от контекста. Има три основни категории възли: IPFS възли, data nodes и libp2p възли за приложения.

  • IPFS възли са програми, които работят на компютър и могат да обменят данни с други IPFS възли. Те имат няколко различни имена, но ние ги наричаме различно, в зависимост от контекста:

    • възел: Използвайте възел, когато се позовавате на отделна точка в мрежата. Това е много общ термин. Например, когато отворите IPFS Desktop, вие установявате себе си като възел с потенциал да взаимодейства с други възли. Виж Конфигуриране на възел.
    • peer: Използвайте peer, когато говорите за връзката на един възел (дори собствения ви) с други възли. Това означава тяхното отношение като равни, без централен орган, така че вашият възел е peer спрямо други peers. Виж Наблюдение на peers и Свързване с доставчици на съдържание.
    • демон: Използвайте демон, когато говорите за състоянието на активност на възел. Когато възелът е онлайн и работи във фонов режим, слушайки за заявки за данните си, се нарича демон. Виж Поставете вашия възел онлайн. Имайте предвид, че IPFS Helia възел в браузър обикновено не се нарича демон. Въпреки това, в контекста на този документ, ние ще наричаме Helia инстанция, действаща като възел в браузър, демон. За повече информация вижте документацията на Helia (opens new window).
    • инстанция: Използвайте инстанция, когато говорите за библиотека или програма, като Go или JS версия, работеща като IPFS възел в определен момент от време. Peer ID е същото, така че това все още е същият възел от гледна точка на IPFS мрежата. Виж Kubo и Helia.

  • Data възли, използвайте data nodes при разговор за действителните части от данни в IPFS, като DAG възли, UnixFS възли и IPLD възли. Когато добавите файл с командата ipfs add myfile.txt, IPFS го разделя на няколко възела, всеки от които съдържа част от файла и е свързан с другите. Виж Merkle Directed Acyclic Graphs (DAGs), Unix File System (UnixFS), и следете документацията за InterPlanetary Linked Data (IPLD) model, която е в процес на разработка.

  • libp2p peer Използвайте libp2p peer, когато говорите за libp2p възли, върху които можете да изграждате приложения. Обикновено те се наричат peers в libp2p, защото предоставя решения за основни peer-to-peer операции като transport, security, routing и discovery на съдържание. Виж концепции

# Видове

Има различни типове IPFS възли. И в зависимост от случая на употреба, един IPFS възел може да изпълнява една от много функции:

  • Релей
  • Bootstrap
  • Делегирано маршрутизиране

# Релей

Ако IPFS възел реши, че е недостъпен от общия интернет, IPFS възлите могат да изберат да използват relay node като вид VPN, за да се опитат да достигнат до недостъпния възел.

# Характеристики на relay възел

  • Имплементира v2 (opens new window) на Circuit Relay протокола.
  • Може да бъде Kubo или Helia възел; въпреки това има и самостоятелни реализации:
    • js-libp2p/circuit-relay (opens new window)
    • go-libp2p-relay-daemon (opens new window)
  • Те се използват и от Kubo, и от Helia възли.
    • Helia възел в браузър не може да говори TCP, така че relay може да помогне за увеличаване на броя на peers, с които може да се комуникира. Helia възел с поддържани в браузъра transports (opens new window) може да говори с Kubo peer без припокриващи се transports, използвайки relay peer, ако този relay поддържа един transport от всеки друг peer:
      1. Поне един browser-supported transport (подходящите transports са включени по подразбиране в Helia browser възли (opens new window))
      2. Поне един Kubo peer supported transport.

# Ограничения на relay възлите:

  • v2 relays са „limited relays“, предназначени да се използват за Direct Connection Upgrade through Relay (opens new window) (известно като hole punching).

Виж p2p-circuit relay (opens new window)

# Bootstrap

И Kubo, и Helia възли използват bootstrap възли, за да откриват peers в DHT.

# Характеристики на bootstrap възел:

  • Всички default bootstrap възли са част от Amino DHT.
  • Списъкът с bootstrap възли, към които се свързва Helia възел, се контролира чрез конфигуриране на опцията peerDiscovery на libp2p (opens new window).

# Ограничения на bootstrap възела:

  • Ако IPFS възел има само един bootstrap възел, посочен в тази конфигурация, и този bootstrap възел спре да работи, IPFS възелът ще загуби достъп до Amino DHT, ако бъде рестартиран.
  • Можете да конфигурирате хранилището на вашите peers в вашата реализация, за да кешира здрави свързваеми peers, така че да можете да се свържете отново след рестартиране, вместо да използвате bootstrap възли. Issue 8856 в Kubo repository (opens new window), който адресира този проблем, предоставя допълнителна информация и контекст.

# Делегирано маршрутизиране

IPFS възлите делегират задачите за маршрутизиране на съдържание и peer към Delegated Routing V1 HTTP API (spec (opens new window)).

Делегираното маршрутизиране през HTTP не е routing система, а общ API за изнасяне на маршрутизиращата работа. Това е полезно в браузъри и други ограничени среди, където е неосъществимо да бъдеш DHT сървър/клиент, контактуващ с много други peers. По-широко, това позволява експерименти и иновации в routing на съдържанието, като същевременно поддържа оперативна съвместимост.

HTTP API (opens new window) може да се използва за разрешаване на заявки за маршрутизиране на съдържание, peer и IPNS име.

# Поддръжка за делегирано маршрутизиране в IPFS реализации

  • someguy (opens new window) е Delegated Routing V1 сървър, който проксира заявки към IPFS Amino DHT и cid.contact Network Indexer (opens new window). IPFS Foundation управлява обществено делегирано routing endpoint, базиран на someguy, с URL https://delegated-ipfs.dev/routing/v1.
  • cid.contact Network Indexer (opens new window) също имплементира Delegated Routing V1 HTTP API.
  • Helia (opens new window) може да бъде настроена да използва delegated routing endpoint.
  • Kubo (opens new window) може да бъде конфигуриран с множество delegated routing endpoints (Kubo като клиент (opens new window)), в допълнение към експонирането на delegated routing endpoint на gateway (Kubo като delegated routing server (opens new window)).
